# v0.2 软件边界

本文档用于把当前阶段收束为可完成、可验收、可重构保护的 `v0.2`。虽然 `VERSION` 当前显示为 `0.8.1`，但从重构准备角度，建议把下一轮稳定化目标命名为 `v0.2`：它不是做更多平台化能力，而是把现有本地工作台能力固定、补齐关键数据底座，并为后续 TypeScript core 做准备。

## 一、必须保留和打磨的功能

### 1. 目标设定

- 保留自然语言目标输入。
- 保留本地规则解析目标类型、目标体重、训练频率、单次训练时长和出差约束。
- 保留当前目标选择。
- 打磨点：目标字段需要在文档和 schema 中固定，避免重构时解析结果字段改名。

### 2. 健身房 / 场地器械管理

- 保留默认健身房、酒店健身房、居家 / 临时场地模板。
- 保留新增健身房、选择当前健身房、删除健身房。
- 保留器械 checklist 和器械图例。
- 保留计划生成按当前器械筛选动作。
- 打磨点：明确 `Gym.equipment` 是器械 ID 列表，暂不引入器械库存、重量范围、型号管理。

### 3. 动作库查看与基础维护

- 保留动作库搜索。
- 保留动作名称、模式、肌群、器械、替代动作、提示、风险和示例链接。
- 保留当前场地可做 / 缺器械展示。
- 保留 CSV 导入时创建极简自定义动作的能力。
- 打磨点：v0.2 可只做“基础维护”定义，不一定实现完整编辑器。至少要固定 `Exercise` 模型，避免继续用临时字段膨胀。

### 4. 训练计划生成

- 保留按目标、场地、身体指标生成训练计划。
- 保留训练日模板：上肢、下肢、全身、推、拉、恢复 / 有氧。
- 保留计划动作字段：动作、组数、次数 / 时长、重量、RPE、休息、备注。
- 保留替代动作按钮和应用记录。
- 打磨点：计划、训练日、计划动作需要增加稳定 ID，减少对数组下标的依赖。

### 5. 今日训练查看

- 保留从当前计划选择训练日。
- 保留今日建议、训练前提醒、当前场地摘要和计划展示。
- 保留从今日页生成 / 刷新计划。
- 打磨点：今日训练应开始向 `WorkoutSession` 靠拢，但 v0.2 不要求做复杂训练计时器。

### 6. 训练整体反馈

- 保留完成度、平均 RPE、疼痛、睡眠、疲劳和备注。
- 保留训练整体反馈生成建议。
- 保留整体反馈触发 revision 候选。
- 打磨点：`sessions` 和旧 `feedback` 的边界需要明确，建议 v0.2 以后以 `sessions` 为主。

### 7. 动作级反馈

- 保留实际重量、实际次数、RPE、动作质量、动作幅度、目标肌肉感觉、限制因素、左右差异、疼痛、自由文本。
- 保留本地规则标签和建议。
- 保留动作历史和动作画像。
- 打磨点：动作日志需要关联 `WorkoutSession`，并为 SetLog 做模型预留。

### 8. 身体指标记录与趋势

- 保留日期、体重、体脂、骨骼肌、腰围、备注。
- 保留列表和趋势图。
- 保留指标趋势参与计划生成、首页联动和周复盘。
- 打磨点：明确指标字段单位和空值规则。

### 9. 饮食自然语言记录

- 保留自然语言饮食记录。
- 保留餐次拆分、食物识别、粗略营养估算、标签、置信度、缺失信息提示。
- 保留饮食建议、趋势图和长期画像。
- 打磨点：明确它是训练辅助饮食记录，不是完整营养数据库。

### 10. 智能建议

- 保留训练、动作、饮食、联动信号生成建议。
- 保留优先级、标签、证据和推荐项展示。
- 保留用户确认后应用计划调整。
- 强约束：AI 或规则都不能静默修改训练计划。

### 11. 周复盘

- 保留最近 7 天训练、饮食、指标联动复盘。
- 保留本周重点、下周动作和调整候选。
- 保留调整候选需确认后应用。
- 打磨点：周复盘候选 patch 类型需要集中定义。

### 12. 长期画像

- 保留动作长期画像。
- 保留饮食长期画像。
- 保留训练前提醒和饮食前提醒。
- 打磨点：画像仍可即时计算，但需要在模型文档中说明不是持久化实体。

### 13. JSON 备份 / 恢复

- 保留全量 JSON 导出。
- 保留 JSON 导入覆盖。
- 保留恢复初始数据。
- 打磨点：导入前至少需要 schemaVersion 检查和基本字段校验。

### 14. CSV 训练计划导入 / 导出

- 保留当前训练计划 CSV 导出。
- 保留 CSV 导入生成训练计划。
- 打磨点：v0.2 不追求完整 Excel 兼容，但要明确 CSV 字段 schema。

## 二、本阶段建议补齐的功能

### 1. 每组级训练记录 `SetLog`

已完成第一版，纳入 v0.2 的数据模型和最小实现。

动作级日志仍保留 `actualLoad` 和 `actualReps` 文本，例如 “24kg / 12/11/8”，以维持快速反馈。当前已新增可选 `sets` 数组；用户不填写每组记录时，系统会尽量从实际重量和实际次数推导。

最小字段建议：

- `id`
- `setIndex`
- `reps`
- `loadKg`
- `rpe`
- `completed`
- `note`

- 当前迁移：

- `schemaVersion: 2` 迁移会为旧动作日志补 `sets: []`。
- 还没有热身组、失败组、目标组完成度等更细字段。
- 重量单位当前隐含为 kg。

### 2. 更清晰的 `WorkoutSession` 数据结构

已完成第一版，纳入 v0.2。

当前 `sessions` 已开始从训练整体反馈扩展为 `WorkoutSession`，动作日志保存时会写入 `sessionId` 并关联当天训练日 session。

- 一次训练的日期、场地、目标、计划、训练日。
- 整体完成度、RPE、疼痛、睡眠、疲劳。
- 训练状态：当前代码支持 `in_progress` 和 `completed`。
- 与 `ExerciseLog` 一对多。

剩余边界：

- `planned`、`skipped`、暂停、计时器、训练时长等状态机还未实现。
- 旧动作日志已通过 `schemaVersion: 2` 迁移补 `sessionId: null`。
- 当前训练日仍主要通过 `dayIndex` 关联，后续需要稳定 `workoutDayId`。

### 3. 训练容量、有效组数、PR 判断的基础数据预留

已完成第一版基础函数和少量 UI 展示，不做完整分析报表。

只有在 `SetLog` 可选存在后，后续才能可靠计算：

- volume load：`load * reps`
- hard sets：RPE 大于等于指定阈值的组
- top set
- estimated 1RM
- reps PR / load PR / volume PR

当前已新增：

- `calculateVolumeLoad`
- `calculateHardSets`
- `detectSimplePr`

动作日志保存时会写入 `volumeLoad`、`hardSets` 和 `simplePr`，动作反馈列表和动作历史摘要会少量展示。

剩余边界：

- `top set`、estimated 1RM 和更细的 PR 规则还未实现。
- 当前 hard sets 规则是第一版粗略判断。

### 4. 数据模型 schema

已完成第一版，纳入 v0.2。

当前已有 `schemaVersion: 2` 和第一版迁移机制。v0.2 仍应继续补充更正式的 schema 文档和导入校验：

- `AppState` schema 草案。
- 每个核心模型字段说明。
- JSON 导入时的最小校验。
- 缺省字段填充策略。

### 5. 数据迁移机制

已完成第一版，纳入 v0.2。

迁移机制不需要引入数据库，也不需要破坏 localStorage。可以先做：

- `CURRENT_SCHEMA_VERSION`
- `migrateState(rawState)`
- v1 到 v2 的默认字段补齐
- 导入 JSON 后也走迁移
- 导入 JSON 先解析和迁移，成功后才覆盖 localStorage

重点是让后续 `WorkoutSession`、`ExerciseLog.sets`、`SetLog` 不破坏旧数据。

### 6. 基础规则测试

已完成第一版，纳入 v0.2。

当前核心规则在 `planner.js`，且没有自动化测试保护。即使仍保持静态运行方式，也可以新增非常轻量的浏览器外测试脚本或 Node 测试脚本，覆盖：

- `parseGoal`
- `generatePlan`
- `analyzeExerciseFeedback`
- `parseNutritionLog`
- `buildWeeklyReview`
- `metricTrend`
- `calculateVolumeLoad` / `calculateHardSets` / `detectSimplePr`
- `stateMigration_v1_to_v2_preserves_data_and_defaults`

测试不应改变应用运行方式，`index.html` 仍要能双击运行。

### 7. TypeScript core 的准备工作

建议纳入 v0.2 的设计和小步准备，不建议本阶段直接全面 TypeScript 化。

可以先做：

- 在文档中冻结模型。
- 将纯函数边界识别出来。
- 后续再新建 `src/core/models`、`src/core/rules`、`src/app/state`、`src/app/storage`。
- 不引入 React / Vue / Tauri / SQLite / FastAPI。

## 三、本阶段明确不做的功能

### 1. 不做云同步

当前定位是本地优先，数据在浏览器 localStorage。v0.2 重点是 schema、迁移和备份，不引入云端数据一致性问题。

### 2. 不做账号系统

账号会引入登录、鉴权、远程存储和隐私合规问题，不符合当前本地工作台阶段。

### 3. 不做社交

当前产品目标是个人训练决策工具，不做动态、关注、排行榜、群组或公开分享。

### 4. 不做公开课程平台

不引入课程售卖、课程库、教练后台或多人管理。

### 5. 不做完整营养数据库

饮食模块只服务训练决策和结构判断，不做精确营养 App。v0.2 不做完整食物库、扫码、微量营养素、品牌食品库。

### 6. 不做医学诊断 / 康复处方

疼痛反馈只用于训练风险提醒、降量、替代动作建议。不能输出医学诊断或康复处方。

### 7. 不做视频动作识别

不做摄像头、视频上传、姿态识别或动作自动评分。

### 8. 不做手机 App

当前 `styles.css` 明确偏桌面布局，`body` 有 `min-width`。v0.2 不解决移动端完整体验。

### 9. 不做华为 / 佳明手表端

手表端会引入设备 API、同步和数据映射，属于后续平台扩展。

### 10. 不立即接入 Python FastAPI

当前应用是零依赖静态页面。v0.2 不引入后端服务，避免破坏双击打开。

### 11. 不立即做 Tauri / SQLite

桌面壳和 SQLite 分别是后续 Phase 5 / Phase 6 规划。v0.2 先把模型、迁移、测试和核心逻辑边界打稳。

### 12. 不让 AI 自动静默修改训练计划

即使后续接入 AI，AI 只能产生结构化候选和解释。计划修改必须经过 schema 校验、规则引擎处理和用户确认。

## v0.2 验收口径

- 双击 `index.html` 仍可运行。
- 当前所有页面可打开，已有核心记录功能不回退。
- JSON 导出 / 导入仍可用。
- CSV 计划导入 / 导出仍可用。
- `WorkoutSession`、`ExerciseLog`、`SetLog` 的模型边界清楚。
- 至少有核心规则 smoke test 或人工验收清单。
- 重构前有可回退基线。
