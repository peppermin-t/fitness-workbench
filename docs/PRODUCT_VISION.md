## 1. 长期愿景

这个软件长期想成为一个本地优先、低录入成本、可解释的个人训练决策工作台。

它的核心不是“记录更多数据”，而是把训练计划、健身房器械、训练执行、动作反馈、饮食记录、身体指标和长期复盘串起来，持续帮助用户做更稳的训练决策：

- 今天在这个场地应该练什么。
- 当前动作是否该加重、降量、替换或保持。
- 饮食和恢复是否正在影响训练表现。
- 体重、体脂、骨骼肌等趋势是否支持当前目标。
- 下一周计划应该小幅调整什么。
- 哪些问题是一次性的，哪些已经成为长期模式。

长期目标是让软件越用越了解用户，但仍保持用户确认、用户掌控和本地优先。

## 2. primarily 服务谁

本软件 primarily 是为单个用户长期使用而定制的个人训练工作台，不以泛用商业健身 SaaS 为目标。

它优先服务这样的使用者：

- 主要进行健身房力量训练。
- 经常需要在不同健身房、酒店健身房、居家或临时场地之间切换。
- 希望训练计划能根据当前器械条件自动调整。
- 需要把训练计划、身体指标、饮食记录、训练反馈和动作级反馈联动起来看。
- 希望训练后用少量字段完成复盘，而不是维护复杂表格。
- 希望所有建议都有依据，并且必须确认后才修改计划。

因此，产品设计优先考虑单个真实用户的长期训练上下文，而不是多人协作、教练 SaaS、课程售卖、社交传播或泛用健身平台。

## 3. 当前核心训练场景

当前核心仍然是力量训练工作台：

- 目标设定。
- 健身房 / 场地器械管理。
- 动作库和替代动作。
- 训练计划生成。
- 今日训练查看。
- 训练整体反馈。
- 动作级反馈。
- 身体指标记录和趋势。
- 饮食自然语言记录。
- 智能建议。
- 周复盘。
- 长期画像。
- JSON 备份 / 恢复。
- CSV 训练计划导入 / 导出。

这些能力共同服务一个闭环：计划 -> 执行 -> 反馈 -> 分析 -> 候选调整 -> 用户确认 -> 下一轮计划。

## 4. 长期个人化方向

用户的真实运动组合不只包含健身房力量训练。长期设计应为更多个人化场景预留空间，但这些方向不纳入当前 v0.2 必做功能。

### 4.1 出差训练

长期需要继续强化：

- 不同健身房 / 酒店 / 居家场地切换。
- 器械受限时的动作替代。
- 出差期间低录入成本训练。
- 出差饮食结构和训练表现联动。

### 4.2 间歇性徒步

徒步可以作为长期画像的一部分，用来理解：

- 一周总体疲劳。
- 下肢训练安排是否需要避开长距离徒步后几天。
- 膝、踝、髋、下背等反馈是否与徒步负荷有关。

当前不做户外路线管理，不做轨迹记录，不做装备清单平台。

### 4.3 越野跑入门或周末山野活动

越野跑和山野活动可以作为长期目标模板或体能标签：

- 下肢耐力。
- 心肺基础。
- 上下坡力量。
- 核心稳定。
- 周末活动后的恢复管理。

当前不做越野赛事管理、不做配速策略平台、不做训练营或社交挑战。

### 4.4 滑雪季腿部、核心和体能维护

滑雪季前后可以作为长期周期目标：

- 股四头肌、臀、腘绳肌力量。
- 核心抗旋转和稳定。
- 膝关节风险提示。
- 下肢耐力和体能维护。
- 滑雪后恢复和下一周力量训练安排。

当前不做滑雪技术教学，不做医学康复处方，不做雪场行程管理。

### 4.5 后续可能的攀岩基础训练

攀岩可作为后续基础训练方向：

- 拉力和肩胛控制。
- 握力和前臂恢复。
- 核心张力。
- 肩肘手指负荷管理。

当前不做攀岩路线管理、不做抱石难度追踪、不做专项伤病康复处方。

## 5. 它不是什么

为了避免长期方向无限膨胀，本软件明确不做：

- 不做泛用商业健身 SaaS。
- 不做云端账号系统作为当前核心。
- 不做运动社交。
- 不做公开课程平台。
- 不做完整体能平台。
- 不做户外路线管理。
- 不做越野赛事管理。
- 不做完整营养数据库。
- 不做医学诊断。
- 不做医学康复处方。
- 不做视频动作识别。
- 不让 AI 或规则静默修改训练计划。

即使未来接入 AI、桌面壳或数据库，产品边界也仍然是个人训练决策辅助，而不是替代教练、医生、康复师或完整运动平台。

## 6. 长期可考虑的扩展方向

长期路线中可以考虑：

- AI 结构化解析目标、训练反馈、动作反馈和饮食记录。
- 更正式的桌面应用体验。
- SQLite 或其他本地数据库。
- Tauri 桌面打包。
- `.xlsx` 训练计划导入。
- 更清晰的数据迁移。
- 手机端快速记录。
- 手表或外部设备数据接入。
- 个人化目标模板，例如出差维持、滑雪季准备、徒步恢复、越野入门、攀岩基础。

这些方向不是当前 Phase 0 / v0.2 的直接执行目标。

当前工程下一步以 [V0_2_SCOPE.md](V0_2_SCOPE.md) 和 [REFACTOR_PLAN.md](REFACTOR_PLAN.md) 为准：先完成 v0.2 稳定化、重构保护、核心模型固定、最小测试基线，再进入正式代码重构。

## 7. 当前阶段原则

当前阶段继续坚持：

- 本地优先。
- Tauri 桌面端是当前运行入口。
- v0.2 阶段不引入 React / Vue / FastAPI；Phase 5 起已开始最小 Tauri 壳接入，Phase 6 起已开始 SQLite 存储桥接。
- `src/app/index.html` 是桌面前端源文件，由构建脚本复制到 `dist/desktop/index.html`。
- 不删除现有功能。
- 不让 AI 或规则静默修改计划。
- 重构前先冻结功能、模型、验收清单和规则用例。

正式重构的第一步应从 `planner.js` 中的纯业务逻辑拆分开始，而不是先改 UI、先上框架或先做平台化。
